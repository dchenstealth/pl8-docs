# PL8 storage
Every PL8 entity is a row in DynamoDB. IssueAttachments are the one entity that
is also bytes, and the bytes live in S3: one bucket per deployment, in the same
account as everything else. See [entities](../entities.md) for the row, its
statuses and its counters; this file is about the bucket.

pl8-services deploys the bucket. pl8-interface signs the URLs a caller uploads
and downloads through, and confirms uploads. pl8-event-handler deletes objects
when rows go away.

## Keys
An attachment's object key is:

```
space/<space_id>/issue/<issue_id>/attachments/<attachment_id>
```

Rules:
* A key MUST be derived from the row and nothing else. The attachment id is a
  UUIDv7 generated by PL8, so no caller-supplied text reaches a key and there is
  nothing in one to escape.
* A key MUST contain the space id, even though the attachment id alone would be
  unique. An issue id is unique only within a Space, so a key naming only the
  Issue would put two Spaces under one prefix — and prefix is the only boundary
  S3 has, so every prefix-scoped IAM policy, lifecycle rule or bulk delete would
  span the deployment rather than one Space.
* A key MUST NOT be stored in place of the ids it is derived from.

Keeping the name out of the key makes the key safe; it is not what makes the
name safe. The name does reach S3, as a signed header rather than a key (see
[Downloading](#downloading)), and what protects that is validation at creation
plus the signature.

## Uploading
An upload is three steps, and PL8 is present only for the first and third.

1. **Initiate.** The caller names the Issue, optionally an IssueComment, and
   declares a name, content type and size. PL8 writes a PENDING row and returns
   a presigned POST: a URL, the form fields to send with it, and the attachment
   id.
2. **Upload.** The caller POSTs the bytes straight to S3. PL8 never sees them,
   which is the point: a 100MB file does not pass through a Lambda.
3. **Confirm.** PL8 does a HEAD against the key and, only if the object is
   there, transitions the row to UPLOADED, writes the size and content type S3
   reports, clears the TTL and increments `num_attachments`.

Rules:
* A presigned POST MUST carry the declared size as an exact
  content-length-range, the same value as both bounds, rather than a range up to
  the limit. S3 then refuses anything but the file the caller described.
* The declared size MUST be at most 100MB, refused at initiate so an oversized
  upload never has a target.
* A presigned POST MUST expire 5 minutes after signing. That bounds how long an
  unused target may sit around, not how long a transfer may run: S3 applies the
  deadline when the request begins, so a slow upload that started in time is not
  cut off.
* Confirm MUST be idempotent, guarded by `status = PENDING`; see
  [entities](../entities.md).
* Nothing MUST depend on the object being absent before an upload. A caller may
  upload twice to the same target, or upload after confirming. The row is what
  PL8 knows, and confirm is the only thing that reads S3.

## Re-signing an upload
A caller returning to a failed upload has a PENDING row and an expired target.
Re-signing issues a fresh POST for the same key. Without it the caller would
initiate again, leaving the first row until its TTL and PL8 storing whatever the
abandoned attempt uploaded.

The case it answers is a target that expired *between* attempts. It is not for a
large upload outrunning its URL, which cannot happen for the reason above.

Rules:
* Re-signing MUST be conditional on the attachment being PENDING. Re-signing an
  UPLOADED attachment MUST fail — a fresh POST for that key would be permission
  to replace confirmed bytes.
* Re-signing MUST NOT change the row: not its id, name, declared size, content
  type, comment link, timestamp or TTL. It is a new token for an unchanged
  intention.
* Re-signing MUST NOT extend the TTL. The 24 hours run from creation, so a
  caller still uploading a day later starts over.

## Downloading
Reading an UPLOADED attachment is one step: PL8 signs a GET and returns the URL
alongside the row. The bytes come from S3 directly, for the same reason they go
there directly.

Rules:
* A signed GET MUST expire 5 minutes after signing, as a POST does.
* A signed GET MUST carry the attachment's name in a signed
  `ResponseContentDisposition`, so the file arrives named as whoever attached it
  named it rather than as a UUID.
* A signed GET MUST NOT be issued for an attachment that is not UPLOADED.
  Reading a PENDING attachment returns the row and no URL at all; PL8 does not
  hand out a URL it knows will 404.
* That absence MUST be what tells a caller there are no bytes yet, and MUST be
  safe to treat that way — a caller needs no reasoning about statuses to know it
  cannot download. It is how the CLI's `attachment get` refuses (see
  [cli](../cli/overview.md)).

## Presigned URLs are not authenticated claims
A presigned URL is a bearer token. It carries a signature made with the signing
Lambda's execution role, so it grants what *that role* can do to *that key*, not
what the caller who asked for it can do. Whoever holds it can use it until it
expires, and there is no revocation short of that.

This is consistent with PL8's model rather than a hole in it: access is plain
AWS IAM, and any principal that can invoke pl8-interface can already read the
whole deployment. A presigned URL is narrower — one key, one operation, five
minutes.

It is worth stating for the same reason [creator](../entities.md#creator) is: it
looks like an identity and is not one. A creator is a label PL8 does not verify;
a presigned URL is an authorization PL8 does not attribute.

Rules:
* A presigned URL MUST be treated as a secret with a five-minute life. Anything
  that logs, stores or forwards one is handing over the access it carries.

## Reaping
Rules:
* Deleting an object MUST be driven by the row going away, never the reverse.
  IssueAttachmentDeleted is sent whenever a row is removed — by a caller, by a
  cascade, or by TTL — and that event is what deletes the object (see
  [events](events.md)).
* TTL expiry MUST be the only thing that reclaims an object uploaded to a target
  and never confirmed. Nothing else knows those bytes exist: PL8 never saw the
  upload, so the row is the only record that a key was ever signed.
* Nothing MUST assume the object exists when the deletion runs. A PENDING row
  usually has no object behind it, so the delete is routinely a no-op and MUST
  treat a missing key as success.

An attachment linked to a comment is swept by two cascades at once and its
object still goes once, because the event comes from the row's removal rather
than from either handler; see [entities](../entities.md). Object deletion is
idempotent regardless — a second DeleteObject writes another delete marker
rather than failing, and that marker is a noncurrent version the 7-day rule
clears.

## Versioning
The bucket has versioning enabled, with noncurrent versions expiring after 7
days. A delete writes a delete marker and the previous version becomes
noncurrent, so bytes are billed for up to a week after they are deleted. Two
consequences: deleting an Issue does not shrink that week's bill, and a deleted
attachment is recoverable by an operator for those 7 days. The second is
deliberate, since an accidental cascade otherwise destroys objects PL8 cannot
get back — but it means a deletion that must be honoured completely is not
honoured by PL8's delete alone.
