# PL8 storage
Every PL8 entity is a row in DynamoDB. IssueAttachments are the one entity that
is also bytes, and the bytes live in S3: one bucket per deployment, in the same
account as everything else. The DynamoDB row is the attachment and the object is
what it points at — see [entities](../entities.md) for the row, its statuses and
its counters. This file is about the bucket.

pl8-services deploys the bucket. pl8-interface signs the URLs a caller uploads
through and confirms uploads. pl8-event-handler deletes objects when rows go
away.

## Keys
An attachment's object key is:

```
space/<space_id>/issue/<issue_id>/attachments/<attachment_id>
```

Rules:
* A key MUST be derived from the row and nothing else. The attachment id is a
  UUIDv7 generated by PL8, so a key is never built from caller-supplied text and
  the attachment's `name` never appears in it. There is nothing to escape, no
  traversal to reject, and no way for one caller's name to collide with
  another's.
* A key MUST contain the space id, even though the attachment id alone would be
  unique. An issue id is only unique within a Space, so a key that named only
  the Issue would put two Spaces' Issues under one prefix. Every prefix-scoped
  thing the bucket will ever want — an IAM policy that grants one team its own
  Space, a lifecycle rule, a prefix delete when a Space is emptied — would then
  span Spaces, and the blast radius of getting one wrong would be the whole
  deployment rather than one Space. The prefix is the only boundary S3 has, so
  it has to be the boundary PL8 has.
* A key MUST NOT be treated as stable identity for anything but its own object.
  It is derived, so it can be recomputed; it is not a handle to be stored in
  place of the ids it is built from.

## Uploading
An upload is three steps, and PL8 is only present for the first and the third.

1. **Initiate.** The caller names the Issue, optionally an IssueComment, and
   declares a name, a content type and a size. PL8 writes a PENDING row (see
   [entities](../entities.md)) and returns a presigned POST: a URL, the form
   fields to send with it, and the attachment id.
2. **Upload.** The caller POSTs the bytes straight to S3. PL8 never sees them,
   which is the point: a 100MB file does not pass through a Lambda's request or
   response, so the size limit is S3's to enforce rather than the interface's to
   survive.
3. **Confirm.** The caller tells PL8 the upload is done. PL8 does a HEAD against
   the key, and only if the object is there transitions the row to UPLOADED,
   writes the size and content type S3 reports, clears the TTL and increments
   `num_attachments` on the Issue and on the linked IssueComment.

Rules:
* A presigned POST MUST carry the declared size as an exact content-length-range
  — the same value as both the minimum and the maximum — not a range up to the
  100MB limit. S3 then rejects anything but the file the caller described, so
  the size on a PENDING row is not a claim the caller can walk back, and a
  caller cannot declare a small file and upload a large one.
* The declared size MUST be at most 100MB. 100MB is also the ceiling of what the
  policy will ever be signed for, so an oversized upload is refused at initiate
  and has no target to be attempted against.
* A presigned POST MUST expire 5 minutes after it is signed. Five minutes is
  time to start an upload, not time to keep one around: S3 applies the deadline
  when the request begins, so a slow upload that started in time is not cut off.
* Confirm MUST be idempotent and MUST NOT be assumed to arrive once. It is
  guarded by `status = PENDING`, which is what makes the counter increments
  happen exactly once however many times it is delivered; the reasoning is in
  [entities](../entities.md).
* Nothing MUST depend on the object being absent before an upload. A caller may
  upload twice to the same presigned target, or upload after confirming; the row
  is the record of what PL8 knows, and confirm is the only thing that reads S3.

## Presigned URLs are not authenticated claims
A presigned URL is a bearer token. It carries a signature made with the signing
Lambda's execution role, so it grants what *that role* can do to *that key* —
not what the caller who asked for it can do. Anyone who comes to hold the URL
can use it until it expires, and S3 cannot tell them apart from the caller PL8
signed it for. There is no revocation short of the expiry.

This is consistent with PL8's model rather than a hole in it: access is plain
AWS IAM, and any principal that can invoke pl8-interface can already read every
Space, Issue and comment in the deployment. A presigned URL is narrower than
that — one key, one operation, five minutes.

It deserves saying plainly all the same, for the same reason `creator` does in
[entities](../entities.md): it is a place where something that looks like an
identity is not one. `creator` is a label PL8 does not verify. A presigned URL
is an authorization PL8 does not attribute. Neither tells you who did anything,
so neither may be relied on to. A URL handed to a third party, pasted into a
log, or left in a shell history is usable by whoever reads it, and treating it
as a secret with a five-minute life is the only correct handling.

## Reaping
A PENDING row carries a 24-hour TTL, and its expiry is what cleans up an upload
nobody finished.

Rules:
* Deleting an object MUST be driven by the row going away, never the reverse.
  IssueAttachmentDeleted is sent whenever a row is removed — by a caller, by the
  cascade from a deleted IssueComment or Issue, or by TTL — and deleting the
  object is what that event triggers (see [events](events.md)).
* TTL expiry MUST be the only thing that reclaims an object uploaded to a
  presigned target and never confirmed. Nothing else knows those bytes exist:
  PL8 never saw the upload, and an unconfirmed row's size and content type are
  only what the caller said they would be. The row is the only record that a key
  was ever signed for, so the row's death has to be what sweeps the key.
* Nothing MUST assume the object exists when the deletion runs. A PENDING row
  usually has no object behind it, so the delete is routinely a no-op and MUST
  treat a missing key as success.

A row is sometimes swept twice and the object still goes once. Deleting an Issue
runs two sweeps across the same attachment: the IssueDeleted handler deletes
every attachment in the Issue's partition, and the IssueCommentDeleted handler
for each of that Issue's comments deletes the attachments linked to that
comment. Only one of them can actually remove the row, and
IssueAttachmentDeleted is sent from the removal rather than by either handler,
so two sweeps still ask for one object delete. The reasoning for the row itself
is in [entities](../entities.md).

What matters on this side is that the ask is idempotent anyway. A DeleteObject
for a key that is not there succeeds, which is what the rule above requires
handling, and a second DeleteObject for a key already deleted succeeds too — in
a versioned bucket it writes another delete marker rather than failing, and that
marker is itself a noncurrent version, so the 7-day rule clears it. Nothing in
the cascade needs an event to arrive exactly once, which is the only reason it
can be built on a bus that promises at least once.

## Versioning
The bucket has versioning enabled, with noncurrent versions expiring after 7
days.

Deleting an object therefore does not reclaim its bytes immediately. A delete
writes a delete marker, the previous version becomes noncurrent, and the storage
is billed until the lifecycle rule removes it up to 7 days later. Two things
follow. Deleting an Issue does not shrink the bill that week, which is worth
knowing before reading a cost graph. And a deleted attachment's bytes are
recoverable by an operator with access to the bucket for those 7 days, which is
deliberate — an accidental `issue delete` cascades to objects PL8 cannot
otherwise get back — but it means a deletion request that has to be honoured
completely is not honoured by PL8's delete alone.
