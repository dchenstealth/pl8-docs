# Entities
## Creator
Every entity a caller creates records a `creator`: who or what created it.

PL8 has no user model. Access is plain AWS IAM, so `creator` is a label
supplied by the caller, not an identity PL8 establishes.

Rules:
* A creator MUST be a non-empty string of at most 256 characters. It never
  composes a key, so its characters are otherwise unconstrained.
* A creator MUST be supplied when the entity is created, and MUST NOT change
  afterwards. Updating an entity leaves its creator alone.
* A creator MUST NOT be treated as authenticated. PL8 does not verify it,
  does not check it against the invoking IAM principal, and enforces nothing
  on the basis of it. Two callers may claim the same creator, and a caller may
  claim any creator it likes. It is provenance for readers, not authorization.

## Issue
An Issue is the fundamental unit of work in PL8.
An Issue:
* MUST belong to a Space
* MUST have a Status
* MUST have a title and description
* MUST have a [creator](#creator)
* MUST track how many IssueComments it has (`num_comments`)
* MUST track how many uploaded IssueAttachments it has (`num_attachments`)

### Status
A Status indicates what state an Issue is in. There are four Statuses:
* TODO
* BLOCKED
* IN_PROGRESS
* DONE

### Status lifecycle rules
* An Issue MUST NOT be allowed to transition from DONE to another status.

## IssueComment
An IssueComment is a note on an Issue: discussion, findings, or a record of
what an agent did.
An IssueComment:
* MUST belong to an Issue, and so to that Issue's Space
* MUST have a body
* MUST have a [creator](#creator)
* MUST track how many uploaded IssueAttachments are linked to it
  (`num_attachments`)
* MAY be updated or deleted

An IssueComment is the Issue's, not the Space's: it is named by the Space and
Issue it belongs to, and it cannot be moved between Issues. A Space is not a
place comments live independently of an Issue.

An IssueComment MAY be created, updated or deleted on an Issue in any status,
including DONE. DONE is terminal for status transitions, not for discussion.

Updating an IssueComment replaces its body. Its id, creator and creation
timestamp are fixed at creation.

### Comment ids
A comment id is generated by PL8 rather than supplied by the caller, and it is
what carries the comment's position in the Issue's history.

Rules:
* A comment id MUST be a UUIDv7.
* A comment's creation timestamp MUST be the one its id carries, read back out
  of the id rather than taken from a second reading of the clock, so the two
  can never disagree about when the comment was written. A UUIDv7 is minted
  from the clock and cannot be asked to carry a timestamp chosen for it, so
  this is the direction that keeps them in step.
* Creating an IssueComment MUST fail rather than replace a comment whose id is
  already in use. A UUIDv7 collision is not a case to reroll past, unlike an
  issue id collision; it is a signal that ids are not being generated the way
  this rule assumes.

### Ordering
IssueComments are ordered by creation timestamp. A listing returns them oldest
first unless it asks for the reverse: oldest first is the default direction, not
the order the thread has.

Rules:
* An Issue's IssueComments MUST be enumerable together, in creation order,
  ascending or descending. Direction chooses which end of the thread a caller
  reads from; it does not change what the order is.
* Ordering MUST be by comment id. A UUIDv7 leads with its millisecond
  timestamp, and a comment's creation timestamp is that same timestamp, so
  ordering by id *is* ordering by creation timestamp.
* Ordering within one millisecond is only as good as what minted the ids. A
  UUIDv7 generator that counts within each millisecond, as Python's does, puts
  comments minted by one process in the order they were written even when the
  clock has not ticked. Two processes minting in the same millisecond are
  ordered arbitrarily, and a clock that disagrees with its peers orders its
  comments by its own reading of the time. This is accepted rather than
  coordinated away, but it is not equally harmless to everyone reading. For a
  reader of a thread, a comment that sorts before its same-millisecond sibling
  is merely mis-ordered, and both are in front of them either way. For a caller
  polling an Issue by taking its next cursor from the last id of a batch, a
  sibling that sorts before that id is not mis-ordered but skipped: it is
  already behind the cursor, so it will never be returned, and a mis-ordered
  comment becomes a dropped one. The last id of a batch is therefore not a
  watermark, and a poller that cannot afford to lose a comment overlaps its
  windows — resumes from slightly behind the last id and discards what it has
  already seen — rather than trusting that nothing can land before it.
* Ordering MUST NOT be by an updated timestamp. Editing a comment does not
  move it in the thread.

Deriving the order from the id, rather than from a separate timestamp, is what
keeps a comment addressable: a comment can be read, updated or deleted from its
id alone, with no need to also know when it was written.

### Referential integrity
No IssueComment may outlive the Issue it belongs to. An Issue's `num_comments`
is what enforces that, atomically with every write that could break it.

Rules:
* Creating an IssueComment MUST fail if its Issue does not exist. The existence
  check and the `num_comments` increment MUST be atomic with the comment write.
* Deleting an IssueComment MUST decrement its Issue's `num_comments` atomically
  with the delete.
* Deleting an Issue MUST delete every IssueComment on it. Unlike a Space,
  whose deletion is refused while it holds Issues, an Issue is deleted whatever
  its `num_comments`, and its comments go with it. `num_comments` MUST NOT gate
  the deletion of an Issue.
* Comments MAY be deleted asynchronously, after the Issue itself is gone. The
  sweep MUST see every comment that was created: an IssueComment cannot be
  created once the Issue is gone, so the set is closed by the time the sweep
  runs, but the sweep MUST read consistently rather than rely on an
  eventually-consistent view of it.
* Maintaining `num_comments` MUST NOT change the Issue's version, so a
  version-fenced Issue update is not failed by comments being added to or
  removed from that Issue.

## IssueAttachment
An IssueAttachment is a file attached to an Issue: a log, a screenshot, a
patch, anything too large or too binary to paste into a comment.
An IssueAttachment:
* MUST belong to an Issue, and so to that Issue's Space
* MAY be linked to one IssueComment of that Issue
* MUST have a name, a content type and a size in bytes
* MUST have a Status
* MUST have a [creator](#creator)
* MAY be deleted

An IssueAttachment is two things kept in step: a row holding the entity
described here, and a stored object holding the bytes. How the object is named,
uploaded and fetched is in [storage](backend/storage.md).

An IssueAttachment is the Issue's, not the IssueComment's: it is named by the
Space and Issue it belongs to, and it cannot be moved between Issues. It MAY
additionally name one IssueComment of that same Issue, to record that it was
attached as part of that comment. The link is fixed at creation and cannot be
added, changed or removed afterwards, because it decides the attachment's
lifetime: an attachment linked to a comment dies with that comment.

Nothing about an IssueAttachment is updatable by a caller. Only confirming an
upload changes a row, and only its status, size and content type.

### Attachment ids
An attachment id is generated by PL8 rather than supplied by the caller. It
carries the attachment's position in the Issue's history, and it names the
attachment's stored object.

Rules:
* An attachment id MUST be a UUIDv7, and an attachment's creation timestamp MUST
  be the one its id carries. Same rule, same reasoning, as
  [comment ids](#comment-ids).
* Creating an IssueAttachment MUST fail rather than replace an attachment whose
  id is already in use. As with a comment id, a collision means ids are not
  being generated the way this rule assumes. It costs more here than for a
  comment: two rows with one id name one stored object, so the second upload
  would overwrite the first's bytes and leave a row describing a file nobody
  attached to it.

### Name, content type and size
Rules:
* A name MUST be a non-empty string of at most 128 characters. It never composes
  a key, so it need not be unique within an Issue.
* A name MUST NOT contain a C0 control character, DEL, `"` or `\`. A name is not
  inert: it is carried to the caller in a signed download header, and those four
  are what could break out of it. Everything else, including spaces and
  non-ASCII text, is allowed; see [storage](backend/storage.md).
* A content type MUST be a bare media type, with no parameters: `text/plain` is
  accepted, `text/plain; charset=utf-8` is not. It reaches a signed header too,
  and a parameter carries quoting rules of its own.
* A content type and a size MUST be present whatever the status. On a PENDING
  attachment they are what the caller declared; on an UPLOADED one they are what
  storage reported.
* A declared size MUST be at most 100MB, and MUST be enforced on the upload
  rather than only on the declaration, so a caller cannot declare one size and
  upload another; see [storage](backend/storage.md).

### Ordering
IssueAttachments are ordered by creation timestamp, oldest first by default.

Rules:
* An Issue's IssueAttachments MUST be enumerable together, and an
  IssueComment's IssueAttachments MUST be enumerable together, in either
  direction. An attachment linked to a comment appears in both listings.
* Ordering MUST be by attachment id, which is ordering by creation timestamp for
  the reason [IssueComment's Ordering](#ordering) gives. Its caveat about
  ordering within one millisecond applies here unchanged, and so does what that
  means for a poller.
* Ordering MUST NOT be by when an upload was confirmed. An attachment takes its
  place from when it was created, so a large file does not sort behind a small
  one attached after it.
* A listing MUST return attachments whatever their status. PENDING rows are part
  of the Issue's state, and a caller that wants only fetchable attachments
  filters on status itself.

### Status
A Status says whether an IssueAttachment's bytes are there. There are two
Statuses:
* PENDING
* UPLOADED

A PENDING attachment MAY have no object behind it: the row is written before the
caller uploads anything, and a caller that never uploads leaves it that way. An
UPLOADED attachment has been verified — confirming goes and looks before it
writes the status.

### Status lifecycle rules
* An IssueAttachment MUST be created PENDING. A caller MUST NOT be able to
  supply a status.
* PENDING -> UPLOADED MUST be the only transition. An IssueAttachment MUST NOT
  transition from UPLOADED back to PENDING, and MUST NOT be created UPLOADED.
* Confirming MUST verify that the object exists before writing UPLOADED, and
  MUST write the size and content type storage reports onto the row, replacing
  what the caller declared.
* The write that sets UPLOADED MUST be conditional on the row's status being
  PENDING, and MUST be atomic with the `num_attachments` increments it drives.
* Signing a fresh upload target for a PENDING attachment MUST leave the row
  alone, and MUST fail once the attachment is UPLOADED. A new target is a new
  token for the same intention, not an amendment to the attachment.
* A PENDING attachment MUST NOT be given a download URL. Reading one returns the
  row and nothing to fetch it with, and that absence is how a caller learns
  there are no bytes yet.

UPLOADED being terminal is what makes `num_attachments` correct. Confirm arrives
at least once, so the `status = PENDING` condition is both the state check and
the record that the increment already happened — the first confirm consumes it
and every later one fails it. A transition back to PENDING would re-arm the
condition and let a replay count the same attachment twice. This is the argument
[IssueStatus](#status-lifecycle-rules) rests on for DONE: a terminal status is
what turns at-least-once delivery into an exactly-once counter update.

A status is therefore not a caller's claim, which is where it parts company with
[creator](#creator). A creator is whatever the caller says it is. A status is set
by PL8 alone, and UPLOADED means PL8 went and looked. The size and content type
a caller declares *are* claims, which is why confirming overwrites both.

### Expiry
A PENDING IssueAttachment expires, so that an upload which is initiated and
never confirmed does not leave a row forever, or bytes nobody can reach.

Rules:
* A PENDING row MUST carry a TTL 24 hours after its creation.
* Confirming MUST clear the TTL, atomically with the transition to UPLOADED. An
  UPLOADED attachment MUST NOT carry one.
* A TTL MUST NOT be extended. Signing a fresh upload target in particular MUST
  leave it where it was: the 24 hours run from creation, and retrying an upload
  does not buy a longer reservation.
* Expiry MUST reap the object as well as the row, by way of
  IssueAttachmentDeleted (see [events](backend/events.md)). It is the only thing
  that reclaims bytes uploaded to a target and never confirmed, since nothing
  else knows they are there.
* Expiring a PENDING row MUST NOT touch `num_attachments`. It was never counted.
* Confirming an expired attachment MUST fail; the caller initiates again.

24 hours is a floor rather than a deadline, since expired rows are reaped on the
store's own schedule. Nothing depends on the delay being short, which is why an
expiry is enough here and a sweep is not needed.

### Referential integrity
No IssueAttachment may outlive the Issue it belongs to or the IssueComment it is
linked to, and none may be created naming either one that is not there. Unlike
IssueComment and Issue, or Issue and Space, no counter enforces that.

Rules:
* Creating an IssueAttachment MUST fail if its Issue does not exist, and MUST
  fail if it names an IssueComment that does not exist. Both checks MUST be
  atomic with the attachment write.
* Those checks MUST be bare existence checks rather than counter increments.
  This is a deliberate departure from the pattern elsewhere in this document,
  where an owner's counter is both the existence check and the bookkeeping. It
  cannot be that here, because `num_attachments` counts only UPLOADED
  attachments: the counters move at confirm, and at creation there is nothing to
  increment.
* A reader MUST NOT treat `num_attachments` as a census of an owner's children,
  the way it may treat `num_comments` or `issue_count`. An owner whose
  `num_attachments` is 0 may still have PENDING IssueAttachments, so anything
  needing to know whether an owner has attachments at all MUST enumerate them.
* Confirming MUST increment `num_attachments` on the Issue, and on the
  IssueComment if one is named, atomically with the transition to UPLOADED.
* Deleting an UPLOADED IssueAttachment MUST decrement the same counters
  atomically with the delete. Deleting a PENDING one MUST NOT decrement
  anything.
* Maintaining `num_attachments` MUST NOT change the owner's version, the rule
  `num_comments` and `issue_count` follow for the same reason.
* Deleting an IssueComment MUST delete the IssueAttachments linked to it.
  Deleting an Issue MUST delete every one of its IssueAttachments, linked or
  not.
* Neither deletion MAY be gated on `num_attachments`. A Space refuses to be
  deleted while it holds Issues; an Issue and an IssueComment take their
  attachments with them.
* Both cascades MAY be asynchronous, after the Issue or the IssueComment is
  gone, driven by IssueDeleted and IssueCommentDeleted (see
  [events](backend/events.md)). Each sweep MUST see every attachment that was
  created — the set is closed, since creation fails once the owner is gone — but
  MUST read consistently rather than rely on an eventually-consistent view.
* Each sweep MUST delete conditionally and MUST treat a row that is already gone
  as success. The two cascades overlap on an attachment linked to a comment,
  which is swept by both, so finding nothing to delete is the normal case rather
  than a fault. Nothing has to arbitrate: whichever loses is a no-op, and the
  object is still deleted once, because IssueAttachmentDeleted is sent from the
  row's removal rather than by either handler.
* Deleting an IssueAttachment row MUST delete its stored object, row first and
  object second (see [storage](backend/storage.md)). Losing the second step
  leaves an object nobody can reach, which costs storage and nothing else;
  reversing the order would leave an UPLOADED row promising bytes that are not
  there, and an UPLOADED attachment is a statement PL8 checked.
## IssueBlocker
Represents a blocking relationship between two Issues. Issues MAY have
blocking relationships across spaces.

Rules:
* When an IssueBlocker is created, the blocked Issue status MUST be transitioned to BLOCKED.
* An IssueBlocker MUST NOT name an Issue with status DONE as the blocking issue.
* An Issue MUST NOT be transitioned out of BLOCKED while it has active IssueBlockers
* When a blocking Issue is transitioned to DONE and the Issue it blocked has no
  other active blockers, the unblocked Issue MUST be transitioned to TODO.
* An IssueBlocker MUST NOT name the same Issue as both the blocking and the
  blocked issue.
* Blocking cycles between distinct Issues (for example A blocks B and B blocks A)
  are permitted. Issues in a cycle are deadlocked, since neither can reach DONE
  while the other blocks it. Deleting one of the IssueBlockers in the cycle is the
  supported remedy.
* When an Issue is deleted, every IssueBlocker naming it MUST be deleted, whether
  it is the blocking or the blocked issue.

## Space
Spaces are places to group Issues.
A Space:
* MUST have an id, a name, and a description
* MUST have a [creator](#creator)
* MUST be enumerable together with every other Space
* MUST track how many Issues belong to it (`issue_count`)

### Space ids
A space id is supplied by the caller rather than generated, because it is what
every Issue names to say which Space it belongs to.

Rules:
* A space id MUST be unique. Creating a Space with an id already in use MUST
  fail rather than replace the existing Space.
* A space id MUST be between 1 and 64 characters drawn from `[A-Za-z0-9_-]`.
  `#` is excluded because it separates key groups.

### Referential integrity
An Issue MUST belong to a Space. A Space's `issue_count` is what enforces that,
atomically with every write that could break it.

Rules:
* Creating an Issue MUST fail if its Space does not exist. The existence check
  and the `issue_count` increment MUST be atomic with the Issue write.
* Deleting an Issue MUST decrement its Space's `issue_count` atomically with the
  delete.
* Deleting a Space MUST fail while its `issue_count` is nonzero, whatever the
  statuses of its Issues. Deleting a Space never deletes or changes Issues; the
  caller deletes them first.
* Maintaining `issue_count` MUST NOT change the Space's version, so a
  version-fenced Space update is not failed by Issue writes in that Space.
