# Entities
## Creator
Every entity a caller creates records a `creator`: who or what created it.

PL8 has no user model. Access is plain AWS IAM, so `creator` is a label
supplied by the caller, not an identity PL8 establishes.

Rules:
* A creator MUST be a non-empty string of at most 256 characters. It never
  composes a key, so its characters are otherwise unconstrained.
* A creator MUST be supplied when the entity is created, and MUST NOT change
  afterwards. Updating an entity leaves its creator alone.
* A creator MUST NOT be treated as authenticated. PL8 does not verify it,
  does not check it against the invoking IAM principal, and enforces nothing
  on the basis of it. Two callers may claim the same creator, and a caller may
  claim any creator it likes. It is provenance for readers, not authorization.

## Issue
An Issue is the fundamental unit of work in PL8.
An Issue:
* MUST belong to a Space
* MUST have a Status
* MUST have a title and description
* MUST have a [creator](#creator)
* MUST track how many IssueComments it has (`num_comments`)
* MUST track how many uploaded IssueAttachments it has (`num_attachments`)

### Status
A Status indicates what state an Issue is in. There are four Statuses:
* TODO
* BLOCKED
* IN_PROGRESS
* DONE

### Status lifecycle rules
* An Issue MUST NOT be allowed to transition from DONE to another status.

## IssueComment
An IssueComment is a note on an Issue: discussion, findings, or a record of
what an agent did.
An IssueComment:
* MUST belong to an Issue, and so to that Issue's Space
* MUST have a body
* MUST have a [creator](#creator)
* MUST track how many uploaded IssueAttachments are linked to it
  (`num_attachments`)
* MAY be updated or deleted

A comment cannot be moved between Issues. It MAY be created, updated or deleted
on an Issue in any status, including DONE: DONE is terminal for status
transitions, not for discussion. Updating a comment replaces its body and
nothing else.

### Comment ids
Rules:
* A comment id MUST be a UUIDv7 generated by PL8, not supplied by the caller.
* A comment's creation timestamp MUST be the one its id carries, so the two can
  never disagree.
* Creating an IssueComment MUST fail rather than replace a comment whose id is
  already in use. A UUIDv7 collision is a bug, not something to retry past.

### Ordering
Rules:
* An Issue's IssueComments MUST be enumerable together in creation order,
  oldest first by default, or newest first.
* Ordering MUST be by comment id, which for a UUIDv7 is ordering by creation
  timestamp. Editing a comment does not move it.

Ordering within one millisecond is best-effort: comments minted by different
processes in the same millisecond sort arbitrarily. The cost falls on pollers.
A caller that resumes from the last id it saw can miss a same-millisecond
comment that sorted before it, so one that cannot afford to lose a comment
overlaps its windows rather than treating the last id as a watermark.

### Referential integrity
No IssueComment may outlive its Issue. The Issue's `num_comments` enforces
that, atomically with every write that could break it.

Rules:
* Creating an IssueComment MUST fail if its Issue does not exist, and MUST
  increment `num_comments` atomically with the write.
* Deleting an IssueComment MUST decrement `num_comments` atomically with the
  delete.
* Deleting an Issue MUST delete every IssueComment on it, whatever its
  `num_comments`. The comments MAY be deleted asynchronously, after the Issue
  is gone, but every one MUST be found.
* Maintaining `num_comments` MUST NOT change the Issue's version, so a
  version-fenced Issue update is not failed by comment activity.

## IssueAttachment
An IssueAttachment is a file attached to an Issue: a log, a screenshot, a
patch, anything too large or too binary to paste into a comment.
An IssueAttachment:
* MUST belong to an Issue, and so to that Issue's Space
* MAY be linked to one IssueComment of that Issue
* MUST have a name, a content type and a size in bytes
* MUST have a Status
* MUST have a [creator](#creator)
* MAY be deleted

An attachment is a record describing a file plus the stored bytes themselves.
How the bytes are uploaded, fetched and deleted is in
[storage](backend/storage.md).

The comment link is fixed at creation. It records that the file was attached
as part of that comment, and it means the attachment is deleted with the
comment. An attachment cannot be moved between Issues, and nothing about it is
updatable by a caller.

### Attachment ids
Attachment ids follow the same rules as [comment ids](#comment-ids).

### Name, content type and size
Rules:
* A name MUST be a non-empty string of at most 128 characters, and MUST NOT
  contain a control character, `"` or `\`. It need not be unique.
* A content type MUST be a bare media type with no parameters: `text/plain`,
  not `text/plain; charset=utf-8`.
* A size MUST be at most 100MB.

A name is restricted because it is signed into download URLs; see
[storage](backend/storage.md). Parameters are refused because PL8 records what
kind of file an attachment is, not how it is encoded.

### Ordering
Attachments are ordered exactly as [comments are](#ordering), by id, and share
the same millisecond caveat.

Rules:
* An Issue's IssueAttachments MUST be enumerable together, and so MUST an
  IssueComment's. An attachment linked to a comment appears in both.
* A listing MUST include attachments of every status.

### Status
A Status says whether an IssueAttachment's bytes are there. There are two
Statuses:
* PENDING: created, and the caller may not have uploaded anything yet
* UPLOADED: PL8 has verified the bytes exist

### Status lifecycle rules
* An IssueAttachment MUST be created PENDING. A caller MUST NOT supply a status.
* PENDING -> UPLOADED MUST be the only transition.
* Confirming an upload MUST verify the bytes exist, and MUST replace the
  declared size and content type with the stored ones. What a caller declares
  is a claim; UPLOADED means PL8 checked.
* A PENDING attachment MUST NOT be given a download URL. Reading one returns the
  attachment with no URL, which is how a caller learns there are no bytes yet.

UPLOADED is terminal for the same reason DONE is: it is what lets a repeated
confirm be recognised and ignored, so `num_attachments` counts each attachment
exactly once.

### Expiry
A PENDING IssueAttachment expires 24 hours after it is created, so an upload
that is started and never confirmed does not linger.

Rules:
* Expiry MUST NOT be extended, including by re-signing an upload.
* Confirming MUST remove the expiry. An UPLOADED attachment never expires.
* An expired attachment MUST be deleted like any other, bytes included.

24 hours is a floor, not a deadline: expired attachments are removed some time
after it passes.

### Referential integrity
No IssueAttachment may outlive its Issue or the IssueComment it is linked to,
and none may be created for either if it does not exist.

Rules:
* Creating an IssueAttachment MUST fail if its Issue, or the IssueComment it
  names, does not exist, checked atomically with the write.
* Confirming MUST increment `num_attachments` on the Issue, and on the
  IssueComment if one is linked, atomically with the transition to UPLOADED.
* Deleting an UPLOADED IssueAttachment MUST decrement the same counters
  atomically with the delete. Deleting a PENDING one MUST NOT.
* Maintaining `num_attachments` MUST NOT change the owner's version, as with
  `num_comments`.
* Deleting an IssueComment MUST delete its linked IssueAttachments. Deleting an
  Issue MUST delete all of its IssueAttachments. Neither is gated on
  `num_attachments`. Both MAY happen asynchronously (see
  [events](backend/events.md)), but every attachment MUST be found.
* Deleting an attachment that is already gone MUST succeed. An attachment
  linked to a comment is swept by both cascades when its Issue is deleted.
* Deleting an IssueAttachment MUST delete its bytes (see
  [storage](backend/storage.md)).

`num_attachments` counts only UPLOADED attachments, so unlike `num_comments` it
moves at confirm rather than at creation, and it is not a census: an owner whose
`num_attachments` is 0 may still have PENDING attachments.

## IssueBlocker
Represents a blocking relationship between two Issues. Issues MAY have
blocking relationships across spaces.

Rules:
* When an IssueBlocker is created, the blocked Issue status MUST be transitioned to BLOCKED.
* An IssueBlocker MUST NOT name an Issue with status DONE as the blocking issue.
* An Issue MUST NOT be transitioned out of BLOCKED while it has active IssueBlockers
* When a blocking Issue is transitioned to DONE and the Issue it blocked has no
  other active blockers, the unblocked Issue MUST be transitioned to TODO.
* An IssueBlocker MUST NOT name the same Issue as both the blocking and the
  blocked issue.
* Blocking cycles between distinct Issues (for example A blocks B and B blocks A)
  are permitted. Issues in a cycle are deadlocked, since neither can reach DONE
  while the other blocks it. Deleting one of the IssueBlockers in the cycle is the
  supported remedy.
* When an Issue is deleted, every IssueBlocker naming it MUST be deleted, whether
  it is the blocking or the blocked issue.

## Space
Spaces are places to group Issues.
A Space:
* MUST have an id, a name, and a description
* MUST have a [creator](#creator)
* MUST be enumerable together with every other Space
* MUST track how many Issues belong to it (`issue_count`)

### Space ids
A space id is supplied by the caller rather than generated, because it is what
every Issue names to say which Space it belongs to.

Rules:
* A space id MUST be unique. Creating a Space with an id already in use MUST
  fail rather than replace the existing Space.
* A space id MUST be between 1 and 64 characters drawn from `[A-Za-z0-9_-]`.
  `#` is excluded because it separates key groups.

### Referential integrity
An Issue MUST belong to a Space. A Space's `issue_count` is what enforces that,
atomically with every write that could break it.

Rules:
* Creating an Issue MUST fail if its Space does not exist. The existence check
  and the `issue_count` increment MUST be atomic with the Issue write.
* Deleting an Issue MUST decrement its Space's `issue_count` atomically with the
  delete.
* Deleting a Space MUST fail while its `issue_count` is nonzero, whatever the
  statuses of its Issues. Deleting a Space never deletes or changes Issues; the
  caller deletes them first.
* Maintaining `issue_count` MUST NOT change the Space's version, so a
  version-fenced Space update is not failed by Issue writes in that Space.
